# Local inference stack: pin, install, measure

One pinned stack on every machine, and one way to measure it, so a number
from the Windows laptop and a number from the Linux laptop mean the same
thing. Companion to `docs/research/local-runtime-and-free-cloud.md`, which
explains *why* Ollama, *why* these models; this file records *what* is
installed and *what the machines actually did*.

Scope: text generation only. Embeddings, indexing and the RAG pipeline are
measured separately.

## The pin

| Thing | Value |
|---|---|
| Ollama | **v0.40.18** (2026-11-24) |
| Linux archive | `ollama-linux-amd64.tar.zst`, sha256 `b82649006cb5b54ed1237fa2d1a26a7f939a4fd03150033759acbff7ff315adf` |
| Windows installer | `OllamaSetup.exe`, sha256 `ad2bb47aa969b21cf8dd81b2d9f9a6d5030270ed242ef55087118c37c510acc2` |
| Report / demo model | `qwen3:4b-instruct-2507-q4_K_M` (library digest `0edcdef34593`, 2.5 GB) |
| Iteration model | `qwen3:1.7b` → `qwen3:1.7b-q4_K_M` (library digest `8f68893c685c`, 1.4 GB) |
| Context | 4096 tokens, fixed |
| KV cache | f16 unless a row says otherwise |
| Sampling | temperature 0, seed 42, `num_predict` 256 |

Models are pulled **by tag**, not by digest: the research doc flags
`model@sha256:` as documented only in source. The digest each machine gets
back from `/api/tags` is recorded in the row instead. If two machines report
different digests, that is a finding to write down, not a glitch to hide.

Server environment, identical on all machines except `OMP_NUM_THREADS`:

| Variable | Value | Why |
|---|---|---|
| `OLLAMA_NUM_PARALLEL` | `1` | one request at a time, so KV cache stays small and numbers are comparable |
| `OLLAMA_MAX_LOADED_MODELS` | `1` | never two models competing for 4 GB |
| `OLLAMA_CONTEXT_LENGTH` | `4096` | matches the per-request `num_ctx` |
| `OLLAMA_KV_CACHE_TYPE` | unset (f16) | set to `q8_0` only via the fallback below |
| `OMP_NUM_THREADS` | physical cores | `lscpu` cores-per-socket × sockets; 8 on Laptop A. Only bites when something spills to CPU, but record it |

## Install

### Laptop A — Linux, RTX 3050 Ti (no sudo)

The tarball installs entirely under `$HOME`. Nothing touches `/usr`.

```bash
mkdir -p ~/.local/opt && cd ~/.local/opt
curl -fL -o ollama-0.40.18.tar.zst \
  https://github.com/ollama/ollama/releases/download/v0.40.18/ollama-linux-amd64.tar.zst
echo "b82649006cb5b54ed1237fa2d1a26a7f939a4fd03150033759acbff7ff315adf  ollama-0.40.18.tar.zst" | sha256sum -c -
mkdir -p ollama-0.40.18
tar --zstd -xf ollama-0.40.18.tar.zst -C ollama-0.40.18
~/.local/opt/ollama-0.40.18/bin/ollama --version
```

`tar --zstd` needs the `zstd` binary; if it is missing, `zstd -dc ollama-0.40.18.tar.zst | tar -x -C ollama-0.40.18`.

Start the server in its own terminal and leave it running:

```bash
export PATH="$HOME/.local/opt/ollama-0.40.18/bin:$PATH"
export OLLAMA_NUM_PARALLEL=1 OLLAMA_MAX_LOADED_MODELS=1 OLLAMA_CONTEXT_LENGTH=4096
export OMP_NUM_THREADS=8    # physical cores
ollama serve
```

Then, in a second terminal with the same `PATH`:

```bash
ollama pull qwen3:4b-instruct-2507-q4_K_M
ollama pull qwen3:1.7b
```

Models land in `~/.ollama/models` (~4 GB total).

### Laptop B — Windows, GTX 1060

Driver must be ≥ 570 on Pascal (it is; confirmed by @sa4fou).

1. Install the pinned build:
   <https://github.com/ollama/ollama/releases/download/v0.40.18/OllamaSetup.exe>
2. **Quit Ollama from the system tray** — otherwise it holds port 11434 with
   default settings and the environment below never reaches the server.
3. From PowerShell, start the server yourself:

```powershell
$env:OLLAMA_NUM_PARALLEL=1; $env:OLLAMA_MAX_LOADED_MODELS=1; $env:OLLAMA_CONTEXT_LENGTH=4096
$env:OMP_NUM_THREADS=6    # physical cores, check Task Manager
& "$env:LOCALAPPDATA\Programs\Ollama\ollama.exe" serve
```

4. In a second PowerShell window:

```powershell
ollama pull qwen3:4b-instruct-2507-q4_K_M
ollama pull qwen3:1.7b
```

`nvidia-smi` ships in `C:\Windows\System32` and is already on `PATH`, so the
script can sample VRAM without extra setup.

## Measure

```bash
python3 scripts/measure_stack.py --label "Laptop A - Linux RTX 3050 Ti" --out laptop-a.json
```

Windows: `py -3 scripts\measure_stack.py --label "Laptop B - Windows GTX 1060" --out laptop-b.json`.

The script prints (a) the machine facts it detected, (b) one markdown table
row per model, (c) fallback commands if a row failed, (d) the full JSON. Paste
all of it into a comment on
[#2](https://github.com/wb21cs/rag-optimization-genetic-algorithms/issues/2);
one person folds the rows into the table below. Do not edit this file from
three branches.

### What the protocol does, and why

* Two fixed prompts, sized to ~512 and ~2048 tokens. The text is identical
  bytes on every machine, so the tokenizer produces identical
  `prompt_eval_count` values — that is what makes tok/s comparable. 2048 is
  the RAG-relevant size; 512 is there to show prefill scaling.
* Prefill and decode rates come from Ollama's own counters
  (`prompt_eval_count`/`prompt_eval_duration`,
  `eval_count`/`eval_duration`), not from a wall clock.
* Per model: unload, one cold run at 2048 (so `load_duration` is real), three
  warm runs at 2048, three warm runs at 512. Medians of the warm runs are the
  reported numbers.
* VRAM is sampled from `nvidia-smi` every 100 ms while runs are in flight.
  Three numbers are reported: idle baseline, absolute peak, and the delta. The
  baseline is the evidence for the research doc's "~3.6 GB usable" assumption,
  and it is what explains "fits on Linux, spills on Windows".
* Residency comes from `/api/ps`: `size_vram / size`. Anything below 99% is a
  spill.

### Verdict bar

| Check | Bar |
|---|---|
| Residency | 100% GPU (≥ 99% `size_vram/size`) |
| Decode | ≥ 15 tok/s |
| Prefill @2048 | ≥ 50 tok/s |
| Cold load | ≤ 60 s |

All four pass → `works`. Anything else → `smoke-only`, with the failing
checks listed. `smoke-only` is a usable result: it says the machine can run
the pipeline but its numbers should not go in the report as representative.

### Fallback ladder

Only if a row comes back `smoke-only` because of a spill:

1. **Quantise the KV cache.** Restart the server with
   `OLLAMA_KV_CACHE_TYPE=q8_0` and re-run that model with `--kv q8_0`.
   Halves KV (~290 MB saved at 4096 ctx on the 4B) and keeps the 4B model —
   the model the report is about.
2. **Drop to 1.7B on that machine only.** Record it as such. Do not silently
   swap the fleet's model.
3. If neither fits, the machine is a smoke-test box and the weakest
   *working* laptop sets the ceiling — which is a finding the report needs.

## Known unknowns

* **Mac GPU path.** Apple Silicon runs Metal; Intel Macs are CPU-only per
  Ollama's docs. The fleet's third machine has not been checked, so no
  ceiling claim can be made for it yet.
* **Windows VRAM overhead.** The idle baseline on Windows is expected to be a
  few hundred MB, not the 15 MiB Linux idles at. The delta column is what to
  compare across machines; the absolute peak is what to compare against 4 GB.
* **Digest pinning by reference.** Pulling `@sha256:` is untested in the user
  docs; hence tag-pull + recorded digest rather than a digest pull.
